## 2. 当前项目结构

这是一个 Rust workspace，包含三个 crate：

| crate | 目录 | 职责 |
| --- | --- | --- |
| `nctool-tpl` | 根目录 `src/` | minijinja 引擎、模板解析、变量提取、数学/NC 过滤器 |
| `nctool-core` | `core/` | 参数模型、校验、注册表、模板清单、生成管线、机床配置 |
| `nctool-cli` | `cli/` | `templates` / `inspect` / `validate` / `render` / `config` / `ui` 命令 |

模板根目录：`templates/`

当前目录约定：

```text

├── turning/
├── grooving/
├── milling/
├── drilling/

    └── index_g420/
```

模板注册名是相对 `templates/` 的路径，例如：

```text

```

`{% include %}` 必须使用相对模板根的完整路径，例如：


### 3.4 引擎缺陷修复

#### 自赋值默认值误判

文件：`src/extract.rs`

现在：

```jinja
{% set R1 = R1 | default(4000) %}
{{ R1 }}
```

会把 `R1` 判为可选。只有外部参数引用参与必选判定，模板局部变量的后续引用不会把它重新标成必选。

保留的刻意语义：

```jinja
{% set total = total + x %}
```

右侧 `total` 在目标声明前求值，仍然是必选参数。

#### 头部注释空白控制

文件：`core/src/manifest.rs`

现在可以正确解析：

```jinja
{# NAME: 示例模板 -#}
```

不会再把名称解析成带尾随 `-` 的字符串。

### 3.5 角度制数学过滤器

文件：`src/renderer.rs`、`src/filters.rs` 等。


## 9. 重要约定和避坑清单

### minijinja map 没有方法

错误：

```jinja
m.get(key, fallback)
m.keys()
m.items()
```

正确：

```jinja
m[key] | default(fallback)
```

### 三角函数必须确认角度制

- 弧度：`x | sin`、`x | cos`、`x | tan`；
- 角度：`x | sin_d`、`x | cos_d`、`x | tan_d`。

迁移 Python 模板时，源项目的 `sin` / `cos` / `tan` 常常是角度制，不能照抄名称。

### 不要用 `default(0)` 掩盖互斥参数

这会把缺参静默变成 `Z0` 或其他错误坐标。项目安全原则是：宁可渲染失败，也不能静默生成错误 G-code。

### `#}` 不能出现在 Jinja 注释正文里

Jinja 会在第一个注释结束标记处终止注释。文档说明中不要在模板注释正文里直接写该字面量，否则后续内容会泄漏到 G-code 输出。

### YAML 反斜杠

双引号中的 `\u` 会被 YAML 当作 Unicode 转义。清单键使用正斜杠，或用单引号包住 Windows 反斜杠路径。

### 配置文件污染测试

不要在仓库根创建 `nctool.toml`。程序会从当前目录向上查找配置，根目录配置会污染不设置 `current_dir` 的 E2E 测试。手动测试优先传：

```bash
--template-dir ./templates
```

### Windows 路径

- Git-Bash `/tmp` 与原生 Windows 路径不互通；探针模板放仓库内；
- 构建前确认没有运行中的 `nctool.exe`；必要时：

```powershell
Get-Process -Name nctool | Stop-Process -Force
```

- 测试进程持有 CLI 二进制时并行构建会触发 `LNK1104`；测试和构建不要并行。

### 输出目录

`output/` 未被 `.gitignore` 忽略，并且已有 UI 原型、截图等项目产物。不要整目录删除，只处理明确属于当前会话的临时文件。

### 12.2 与 §6.1 建议不同的三处决策（均已在代码注释写明理由）

§6.1 建议"`Choice` 只接受 `ParamValue::String`"，但 §6.2 又要求"options 中有数字时
比较实际变体和值"——只收 `String` 会让数值枚举（`U_Q` = 0/8/10/12.5）先被类型检查
挡掉、永远走不到白名单比较。故：

1. **`Choice` 的类型匹配放宽为"任意标量"**（String/Number/Integer/Bool），`List` 除外。
   真正的约束是白名单而非类型。**副作用**：填错类型的标量报 `NotInOptions` 而非
   `TypeMismatch`（提示更贴近真实原因）。
2. **`options` 对所有类型生效**，不只 `Choice`；`Number + options` 即数值枚举。
   空列表 / `None` = 不约束（旧规格行为完全不变）。
3. **数值/整数跨变体按数值相等**：`Integer(8)` ≡ `Number(8.0)`。CLI/JSON 常把 `8`
   解析成 `8.0`，按变体严格比较是**假拒绝**且不会放行错误值。文本 `"8"` 与数值 `8`
   仍是不同候选项，不做隐式归一化。

另按 §6.2 的建议拆出独立的 `check_value_options()`，且**排在区间/整数检查之前**——
`check_value_constraints()` 对非数值类型在 `as_f64()` 处提前返回，字符串枚举塞进去
等于永不执行。

### 13.5 与方案文档的设计偏离（需知悉）

1. **不做独立的 `templates/variables.yaml`**，改为**解析模板头部 `{# PARAMS: #}`**。

### 14.1 为什么这一轮必须引入变量库

§13.5 曾决定"不做独立 `variables.yaml`，改为解析头部 `{# PARAMS: #}`"。这轮看了源库数据后

- 源库是**按变量名**的全局表（62 个变量），而 19 个 INDEX 模板的头部**没有类型列**

| 清单 `params` | 本模板 | 本模板的显式覆盖（最高优先级） |

## 15. 第四轮：派生参数模块（把查表从模板搬到 Rust）

按 §14.7 第 1 项（`read_only` / `associations`）落地。**结论：这两个概念在能真正
生效之前都需要一个"派生计算"载体**，因此本轮先建载体本身，并用一个真实用例打通。

### 15.1 为什么先做派生载体

`read_only`（源库 22 个变量带此标记）在源项目的含义是"由机床设置/派生计算决定，
用户不可编辑"；`associations`（联动参数）则是"改了 A 就自动定 B"。两者要真正生效，
都必须有地方**把值算出来**——而项目核心原则恰好是「模板只做变量替换，计算在
Rust 侧完成」。所以载体就是 `core/src/derive.rs`，`read_only`/`associations` 是它的
两种用例，不必单独造字段。

**因此本轮刻意没有新增 `ParamSpec.read_only` 字段**：一个不产生任何行为的字段
只会误导读者（详见 §15.5 的偏离说明）。

### 15.2 首个用例：`tip_model → tip_depth`

`machines/index_g420/dg_cal_ir9.j2` 原本在模板里内嵌 12 项查表：

```jinja
{% set tip_depth_map = {'B4': 8.51, 'B6.3': 12.82, ...} %}
{% set tip_depth = tip_depth_map[tip_model|default('DM24')]|default(29.61) %}
```

两个问题：① 数据表写在模板里，改表要改模板、无法单独 review；② minijinja 的 map
没有任何方法（约定 R6），只能写成 `map[k] | default(v)` 绕，模板读起来是"绕引擎限制"
而不是业务逻辑。

现在表搬到 `templates/variables.yaml` 的 `derive` 规则里，模板只写 `{{ tip_depth }}`。

### 15.5 与方案文档的偏离

| 方案要求 | 本轮做法 | 理由 |

| `ParamSpec.read_only` | **未加该字段** | 源库的 `read_only` 分两类：可派生的（用 `derive` 建模）与由调用方预生成的（10 个轨迹段参数，保持普通必选）。加一个不产生行为的字段只会误导；`read_only` 的"用户不可编辑"语义已由 `derive` 的"派生值恒胜 + 警告"覆盖 |

### 16.4 本轮引入的约定（写代码时要守）

1. **`SpecInert` 覆盖两类"永不生效"**：参数名未引用、约束与类型不匹配。两者处置相同
   （去改配置），故共用一个类别；但与 `Unused`（用户多传参数，无副作用）**必须分开**。
2. **参数值渲染只有一个实现**：`ParamValue::display()`。报错、`inspect`、候选值展示
   三处口径必须一致——各写一份必然漂移。
3. **规格字段的 JSON 形状只有一个来源**：`server::spec_json`（`pub(crate)`）。
   新增规格字段时改这一处，`inspect` 与 Web UI 自动同步。
4. **`--param` 归一顺序：显式后缀 > 白名单命中 > 声明类型 > 启发式**。
   前端 `coerceParamValue` 与后端 `coerce_param_value` 保持同一顺序。
5. **改 UI 必须同时改两份**（`ui/index.html` + `cli/ui/index.html`），有测试兜底。
