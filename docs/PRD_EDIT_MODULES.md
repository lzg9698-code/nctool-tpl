## 1. 产品目标

### 1.1 三个模块共同解决什么问题

当前 nctool 已打通"**选模板 → 填参数 → 校验 → 渲染 → 导出**"的**消费链路**（阶段 C/D 完成，UI 验收 37/37）。但**生产链路的供给侧仍是断的**：

- 模板：只能手改 `.j2` 文件（`templates new` 只给骨架，无改/复用）。
- 机床：3 个内置预设**明确不可改**，自定义只能手写 `nctool.toml`。
- 预设：只能在浏览器 localStorage 里存，CLI 看不到、换机器就丢、不随模板演进。

结果是：**工艺工程师一旦想"把现有模板改一改给新零件用"或"给新机床配一套约定"，就必须离开工具、去手写文件**——而这恰恰是最容易写错（也是撞刀风险最高）的一步。

### 1.2 价值主张（一句话）

> **把 nctool 从"能用的渲染器"补齐成"能维护资产的模板工作台"——让模板、机床、参数集三份资产都能在工具内创建、修改、复用，且所有写入都受与渲染同源的校验保护。**

### 1.3 三个正交目标

| 目标 | 说明 | 对应模块 |
|---|---|---|
| **G1 资产可维护** | 模板 / 机床 / 预设都能在工具内创建与修改，不再依赖手写文件 | 一、二、三 |
| **G2 复用可追溯** | "派生自哪份资产、基于哪个版本"可查；复用不产生静默分叉 | 一、二、三 |
| **G3 写入不降级安全** | 写操作不削弱既有防线（P1–P4、严格渲染、golden、退出码契约），不引入新的静默出错路径 | 全局 |

## 3. 模块一：模板编辑

### 3.1 范围

**做：**
- 在工具内**新建**模板（骨架 + 落清单条目 + 可选目录分类），且新建后**立即可渲染**。
- 在工具内**修改**已有模板源码并**安全保存**（写回 `.j2`）。
- **复用/派生**：以现有模板为蓝本另存为新模板（新名 + 新清单条目）。
- **重命名**模板（含清单键同步）。
- 保存前**强制校验**（`inspect` + `validate`），校验不通过不得静默保存。
- 编辑**头部 `{# PARAMS: #}` 参数表**（结构化，P1）。

**明确不做：**
- ❌ **删除模板**（破坏性、影响 golden 与清单一致性；如需删除，走 CLI 显式 `--force` + 二次确认，单列需求，不进本模块 P0）。
- ❌ **目录/分类的新建与移动**（分类由目录推断，移动会改变注册键 → 影响清单与 golden；P2 再议）。
- ❌ **`include` 片段（`_` 前缀）的可视化管理**（片段是"不完整、不可单独渲染"的资产，需独立的依赖图能力；P2）。
- ❌ **在浏览器内对服务端模板直接落盘**（见 §8：默认走 CLI 写盘，UI 不做自由文本落盘）。
- ❌ **在线协同 / 多用户编辑 / 版本控制**（工具定位是本地开发工具，非协作平台）。

### 3.2 用户故事（角色 = 工艺工程师，懂 G-code）

| # | 故事 |
|---|---|
| US-1.1 | 作为工艺工程师，我想**基于现有 `drill_cycle` 派生一个"深孔啄钻"模板**，以便复用已有写法、只改差异部分。 |
| US-1.2 | 作为工艺工程师，我想**在工具里改模板的坐标计算并立即看到新 G-code 预览**，以便不用切到编辑器再切回来。 |
| US-1.3 | 作为工艺工程师，我想**保存前就知道这个模板会不会渲染失败**（缺参数/类型/越界），以便不把坏模板存进模板库。 |
| US-1.4 | 作为工艺工程师，我想**给模板改个名**，以便命名与工艺习惯一致，且清单/调用关系不被打断。 |
| US-1.5 | 作为工艺工程师，我想**让模板的必选/可选参数在头部声明清楚**，以便同事填参时不会漏项。 |

### 3.3 关键操作流程

> 每条流程含**正常路径 + 失败/回退路径**。默认落位为 **CLI 为主**（见 §8），UI 仅做轻量入口。

**F1 新建模板**
1. 用户给出模板名 + 可选分类（目录）。
2. 校验模板名合法性（复用 `validate_template_name`：拒路径穿越、拒非法字符）。
3. 若同名已存在 → **中止**并提示（不覆盖）。若分类目录不存在 → 创建。
4. 生成骨架源码（含 `{# NAME/DESCRIPTION/PARAMS #}` 头部占位）。
5. 写盘（原子写：临时文件 + rename，避免半成品）。
6. （P1）追加清单条目到 `templates.yaml`；若清单加载失败 → 降级为"仅建文件 + 警告"（沿用 D13 降级哲学），并提示用户手补清单。
7. 自动执行 `inspect` 展示参数表，提示下一步填参。

- **失败/回退**：写盘失败（权限/只读）→ 报错 + 退出码 3（IO），**不留下半成品**；清单写入失败 → 文件保留 + 警告 + 人工补录提示。

**F2 打开并修改**
1. 用户选择模板 → 展示当前源码 + 当前参数规格（`inspect` 结果）。
2. 用户编辑（CLI：调 `$EDITOR` 或 `--from-file`；UI：只读展示 + "在外部编辑器打开"）。
3. 保存时先做**写前校验**：
   a. 语法解析（`parse`）→ 失败：报行列 + 中止保存。
   b. `inspect` 参数提取 → 展示必选/可选/条件必选变化。
   c. `validate`（用当前模板的**样例参数或最近一次参数**）→ 有 Error 则**阻断保存**并展示报告。
4. **并发覆盖防护**：写前比对文件 mtime/内容指纹（乐观锁）。若磁盘内容与"打开时快照"不一致 → 中止并提示"文件已被外部修改"，给出 diff，让用户选择"覆盖 / 放弃 / 另存"。
5. 原子写回。
6. （P1）写后自动 `validate` + 提示是否刷新 golden 基线（人工复核，见 §9）。

- **失败/回退**：校验失败 → 保存被拒，编辑内容保留在内存/临时文件，用户可继续改；并发冲突 → 不覆盖，提供另存为分支。

**F3 复用派生**
1. 用户选源模板 + 输入新名。
2. 复制源码 + 复制源模板的清单条目（**含 `params` 覆盖层**）→ 改写清单键为新路径。
3. 清理"派生痕迹"：更新头部 `{# NAME #}`，提示"这是 `X` 的派生副本"。
4. 走 F2 的写前校验 + 写盘。

- **失败/回退**：新名冲突 → 中止；源模板不可读 → 报错。
- **语义要求**：派生**不自动同步**后续源模板变更（避免隐式耦合）；是否标记"派生自 X"由用户决定，默认**写入头部注释**便于追溯（G2）。

**F4 重命名**
1. 用户给出新名。
2. 校验新名 + 检查目标不存在。
3. 重命名文件；同步改 `templates.yaml` 的键；扫描并**警告**所有 `{% include %}` 了旧名的模板（不自动改，避免误伤——`include` 是显式全路径）。
4. 走写前校验。

- **失败/回退**：存在引用 → 提示清单，用户确认后再改，或改后输出待修复引用列表。
- **约束**：重命名不得改变模板的**注册键语义**（路径即键），故重命名 = 移动文件，须同步清单与引用检查。

**F5 保存**
- 见 F2 第 3–5 步；统一为"**校验 → 冲突检查 → 原子写 → 报告**"四段。

**F6 校验**
1. `parse` → 2. `inspect`（参数表 + include 穿透）→ 3. `validate`（需样例参数）。
- 输出沿用 `IssueKind` 结构化类别 + 行列定位，**不得**按消息文本判断（D7）。
- 退出码沿用既有矩阵（校验失败 = 1）。

## 4. 模块二：机床配置编辑

### 4.1 范围

**做：**
- **录入**：新建自定义机床，**默认从 `generic` 预设复制**为基线（避免漏键）。
- **调整**：按 20 键 schema 逐键编辑；`Choice` 键用枚举控件；整数键校验整数与上界。
- **保存**：落到 `nctool.toml`（`[machine.<id>]`），使 **CLI 与 UI 共用同一份**。
- **校验**：键名（对 `KNOWN_CONFIG_KEYS`）、`Choice` 合法性、**完整性**（模板引用的键是否齐）。
- **试渲染验证**：用目标模板 + 该机床渲染一次，作为"能上机"的前置检查。
- **派生语义**：内置预设**不可改**；要改就"派生一份自定义机床"。

**明确不做：**
- ❌ 修改 3 个内置预设（`generic`/`wfl_m65`/`index_ms40`）——这是刻意语义。
- ❌ 对模板不引用的"自由扩展键"做强校验（未知键仍按现状**告警不阻断**，因为自定义机床合法可带扩展键）。
- ❌ 从 UI 直接改**全局配置**（`%APPDATA%` / `$XDG_CONFIG_HOME`）——P0 只写项目 `nctool.toml`，全局写入 P2。
- ❌ 机床预设的"工艺正确性背书"（预设仍未经真实工艺评审，见 §9）。

### 4.2 用户故事

| # | 故事 |
|---|---|
| US-2.1 | 作为工艺工程师，我想**照着 `generic` 派生一台 HERO X9 的机床配置**，以便只改少数几项（如 5 位行号、`G54.1`）而不漏键。 |
| US-2.2 | 作为工艺工程师，我想**在界面上看到每个配置键的含义与类型**，以便不用记 20 个键名。 |
| US-2.3 | 作为工艺工程师，我想**保存前就知道这台机床能不能让目标模板渲染成功**，以便不存下一台"一用就报未定义变量"的机床。 |
| US-2.4 | 作为工艺工程师，我想**改单位制/进给模式时只能选合法值**，以便不会写出 `units=inch` 这种非法值。 |
| US-2.5 | 作为工艺工程师，我想**确认内置预设没有被改动**，以便复用同一台机床时结果稳定可复现。 |

### 4.3 关键操作流程

**F7 录入（新建自定义机床）**
1. 用户输入机床 `id`（`vendor` / `model` 可选）。
2. 校验 `id` 合法且不与内置预设 / 现有自定义机床重名。
3. 系统**以 `generic` 为基线预填全部 20 键**，并标注每键"来自 generic"。
4. 用户逐项调整。
5. 走 F8 校验。
6. 写入 `nctool.toml` 的 `[machine.<id>]`（原子写；项目配置优先）。
7. 提示生效方式（`--machine <id>` / UI 下拉），并建议试渲染。

- **失败/回退**：`nctool.toml` 不存在 → 走 `config init` 等价流程创建；已存在同名段 → 拒绝覆盖或进入"编辑"流程。

**F8 调整与校验**
1. **键名校验**：对 `KNOWN_CONFIG_KEYS` 比对，未知键 → 告警（沿用现状：不阻断）。
2. **Choice 校验**：`units ∈ {metric, imperial}`、`feed_mode ∈ {G94, G95}` → 非法值**阻断保存**（P0；比现状"仅警告"更严，因为这是新录入面，不能让非法值落盘）。
3. **整数键校验**：`program_digits` / `line_number_digits` / `max_spindle_rpm` 必须整数；`line_number_digits` 提示会被夹紧到 `[1,32]`（说明其内存安全含义）。
4. **完整性校验（关键）**：扫描"该机床被选中时可见/被引用的模板"，收集其用到的全部 `{{ machine.<key> }}` 键，与用户配置求差集。
   - 缺键 → **阻断保存**并列出缺失键 + "建议以 generic 为基线补齐"。
   - 理由：模板对 `machine.xxx` 是**裸引用无 default 兜底**，缺键会让严格渲染**直接失败**（这是刻意防线，不改）。
5. 输出校验报告（结构化），全部通过才允许保存。

- **失败/回退**：任何阻断项未清 → 不落盘，编辑内容保留。

**F9 保存**
- 原子写 `nctool.toml`；保存后 `config show` 的"配置警告"段必须为空。
- 并发防护同 F2（mtime/指纹乐观锁）。

**F10 试渲染验证**
1. 用户选一个目标模板（或"该机床可见的全部模板"）。
2. 用该机床 + 该模板的样例参数执行 `validate` + `render`。
3. 展示结果：成功 → 展示 G-code 预览；失败 → 展示报告（缺参/未定义键/Choice 非法）。

- **语义**：试渲染**不能替代**真实空运行/工艺评审（§9 安全提示必须保留）。

### 4.4 验收标准

- [ ] AC-2.1 新建自定义机床默认预填全部 20 键，且来源标注为 `generic`。
- [ ] AC-2.2 内置 3 预设**无法**被修改（UI 无入口 / CLI 拒绝），且代码层仍不可变。
- [ ] AC-2.3 `Choice` 键只能选合法值；非法值**无法保存**。
- [ ] AC-2.4 缺键时**阻断保存**，并列出"当前模板需要的键"清单。
- [ ] AC-2.5 保存后 `nctool config show` 无警告；`nctool machine show <id>` 显示完整键值。
- [ ] AC-2.6 保存后 CLI 与 UI **都能**选到该机床（同一份 `nctool.toml`）。
- [ ] AC-2.7 用该机床 + 目标模板试渲染，结果与 CLI `render --machine` **逐字节一致**。
- [ ] AC-2.8 未知键仍只告警不阻断（保留扩展键语义）。
- [ ] AC-2.9 `line_number_digits` 超大值仍被夹紧到 32（既有内存安全契约不破）。
- [ ] AC-2.10 保存写入不破坏 `nctool.toml` 中其它段（合并而非整体覆盖）。

## 5. 模块三：预设参数编辑

### 5.1 范围

**做（在既有 localStorage 基线之上）：**
- **保存当前参数集为预设**（沿用现有入口；新增：保存前校验 + 只存有效参数）。
- **命名与重命名**（新增重命名；处理重名）。
- **快速应用**（沿用 chips；新增：应用前差异预览）。
- **删除**（沿用；新增二次确认）。
- **导入 / 导出**（新增；跨机、备份、评审用）。
- **与模板的挂载关系**（沿用"预设 = 模板 × 参数值"；新增跨模板复用）。
- **陈旧预设处理**（新增：参数随模板演进失效的识别与处置）。
- **持久化边界**（新增：在 localStorage 之外提供**文件/服务端可选后端**，使 CLI 可见、可版本化）。

**明确不做：**
- ❌ 云端同步 / 多用户共享。
- ❌ 预设内嵌派生结果（派生值由 Rust 侧现算，不冻结进预设——否则会与源参数不一致）。
- ❌ 用预设绕过校验（预设值必须与手填值走**同一套校验**，P3/P4）。

### 5.2 用户故事

| # | 故事 |
|---|---|
| US-3.1 | 作为工艺工程师，我想**把"钻孔 D10×3 深"存成命名预设**，以便同批零件重复使用。 |
| US-3.2 | 作为工艺工程师，我想**从模板卡直接点预设 chip 载入**，以便"复用发生在选模板之前"。 |
| US-3.3 | 作为工艺工程师，我想**把预设导出成文件带到另一台机器**，以便换电脑不丢。 |
| US-3.4 | 作为工艺工程师，我想**知道某个预设因为模板改了参数名而失效**，以便修好而不是拿到错误程序。 |
| US-3.5 | 作为工艺工程师，我想**把 A 模板的预设套到 B 模板上**（参数名兼容时），以便少填一遍。 |

### 5.3 关键操作流程 + 必答语义

**F11 保存当前参数集为预设**
1. 用户填参 → 触发保存（`⌘/Ctrl+S` / 按钮）。
2. 输入/确认名称；重名 → 提示"覆盖 / 改名"。
3. **保存前校验**：对当前模板规格校验当前参数集。
   - 有 Error → 提示"当前参数不合法，仍要保存？"（默认**阻止**，允许显式强制）。
   - 只保存**当前模板规格里存在**的参数（过滤掉 UI 残留的无效键）。
4. 写入预设存储；预设结构 = `{ name, template, params, createdAt, specFingerprint }`（新增 `specFingerprint` 用于陈旧检测）。

- **回退**：无模板选中 → 拒绝保存。

**F12 命名与重命名**
1. 重命名：改 key，校验新名非空、不冲突。
2. 保留原 `template` 绑定与参数。

**F13 快速应用**
1. 点 chip → **先展示差异预览**：将写入哪些参数、将覆盖哪些当前值、模板是否需要切换。
2. 用户确认 → 应用（若预设绑定的是另一模板，先切模板再填参）。
3. 应用后走一次 `validate` 展示结果。

- **回退**：应用后校验失败 → 展示报告，允许"撤销回应用前"。

**F14 删除**
- 二次确认；提示"此操作不可撤销"（P2 可加回收站）。

**F15 导入 / 导出**
- 导出：单条或全部 → JSON 文件（含 `template` 绑定与 `specFingerprint`）。
- 导入：解析 → 逐条做**陈旧检测**（模板是否存在、参数名是否仍有效）→ 报告"可导入 / 需修复 / 跳过"，由用户确认。
- 约束：导入文件大小上限；导入**不执行**任何脚本（纯数据）。

**F16 与模板的挂载关系**
- 预设 = **特定模板 × 特定参数值**（沿用现状的 `template` 字段）。
- 模板卡 chips 仅展示**匹配当前模板**的预设（沿用）。

**F17 跨模板复用**
1. 用户选"应用到另一模板"。
2. 系统计算两模板参数名**交集**，明确列出：
   - 可直接复用（名字与类型一致）；
   - 名称一致但类型/约束不同（需人工确认，不静默转换）；
   - 目标模板需要但预设没有（标为缺失，提示补填）。
3. 用户确认后才应用；**不自动丢弃**，明确告知。

#### 5.3.1 必答语义

| 问题 | 决策（默认假设，待确认见 §10） |
|---|---|
| **存储位置与持久化边界** | **三层**：① localStorage（现状，零配置，默认可用，但**明确标注"仅本浏览器"**）；② **文件后端**（项目内 `presets.yaml`/`.json` 或配置目录），使 CLI 可见、可进版本控制（P0）；③ 服务端 API（`nctool ui` 提供读写端点，与文件后端共用同一内核，符合 P4 单一来源）。**不允许**把"仅 localStorage"当唯一后端（否则 CLI 永远看不到、换机即丢）。 |
| **预设值 vs 规格默认值** | **预设值 = 用户显式提供 → 优先级高于规格 `default`**。规格默认值**只在参数未提供时**兜底。即：应用预设时，预设内出现的参数**不被规格默认值覆盖**。 |
| **预设值 vs 派生参数（derive）** | **派生值恒胜**（与现有语义一致：调用方提供派生参数 → 派生值覆盖 + `ShadowedSystemVar` 警告）。预设**不得冻结派生结果**；若预设含派生参数名，应用时提示"该值会被派生覆盖"。 |
| **预设值 vs 校验** | 预设值照常过全部校验（类型/白名单/区间/有限性）。**预设不是绕过校验的后门**。 |
| **陈旧预设（参数名随模板演进失效）** | ① 保存时记 `specFingerprint`；② 载入/导入时对比当前模板规格：失效参数名 → **不静默应用**，标记为"陈旧"，列出失效项；③ 用户可"清理失效项并保留其余"或"放弃"；④ 目标模板**新增的必选参数**缺失 → 提示补填。 |
| **跨模板复用** | 允许，但**必须先算交集并显式告知**（见 F17）；名称同类型不同 → 不静默转换。 |

### 5.4 验收标准

- [ ] AC-3.1 保存预设后，刷新页面 / 重启浏览器仍可载入（持久化后端生效）。
- [ ] AC-3.2 预设可被 **CLI 列出/导出**（文件或服务端后端存在时）。
- [ ] AC-3.3 重命名预设不丢失参数与模板绑定；重名被拒绝或明确确认。
- [ ] AC-3.4 载入预设前展示差异预览；应用后可撤销。
- [ ] AC-3.5 模板参数名变更后，载入旧预设时**标记陈旧**并列出失效项，不静默应用。
- [ ] AC-3.6 跨模板应用时，列出可复用/需确认/缺失三类，用户确认后才写入。
- [ ] AC-3.7 预设值**不会被规格默认值覆盖**；派生参数会被派生值覆盖并给出警告。
- [ ] AC-3.8 导出→导入往返后，预设内容与 `specFingerprint` 一致。
- [ ] AC-3.9 预设值走与手填值相同的校验；非法预设值无法静默应用。
- [ ] AC-3.10 预设名称/参数含特殊字符时，UI 无 XSS 注入点（沿用 `esc()` 基线）。

## 6. 模块之间的关联关系

### 6.1 共享的概念与数据

| 概念 | 在三个模块中的角色 |
|---|---|
| **参数规格（ParamSpec）** | 模板模块**定义**它（头部 `{# PARAMS: #}` / 清单 `params` / `variables.yaml` 三来源）；预设模块**消费**它做校验与陈旧检测；机床模块不直接用它，但影响"模板是否可渲染"。 |
| **模板** | 模板模块是**主体**；预设模块是"模板 × 参数值"的从属物；机床模块的**完整性校验**以"模板引用的 `machine.*` 键"为输入。 |
| **机床（MachineConfig）** | 是**渲染上下文的一部分**（`{{ machine.xxx }}` 系统注入变量）；模板可引用它；预设**不含**机床（预设只存参数值）。 |
| **渲染上下文** | `参数集（派生+默认兜底）+ machine`。三者最终都汇入这一处。 |
| **校验（IssueKind）** | 三者共用同一内核（P4）：模板保存前、机床试渲染、预设应用，都走 `validate`。 |

### 6.2 典型组合场景

| 场景 | 涉及模块 | 说明 |
|---|---|---|
| **换机床 → 同一模板重新出程序** | 二 × 一 | 改机床后，模板不变、参数可复用（预设或手填），仅 `machine.*` 变化 → 输出不同编程约定。**要求**：机床完整性校验保证不缺键。 |
| **模板 A 的预设能否用于模板 B** | 三 × 一 | 仅当参数名交集可对齐时可用；否则需人工映射。预设的 `template` 绑定是**默认约束**，跨用需显式操作。 |
| **派生模板 + 派生机床** | 一 × 二 | 新零件（派生模板）+ 新机床（派生机床）→ 各自派生，互不隐式耦合。 |
| **改模板参数 → 预设失效** | 一 → 三 | 模板演进是"因"，预设陈旧是"果"；用 `specFingerprint` 建立可检测的因果链。 |
| **改机床 → 模板仍可渲染** | 二 → 一 | 机床改键名/缺键会直接让模板严格渲染失败；这是 §4.3-F8 完整性校验要提前拦住的事。 |

### 6.3 依赖方向与实施先后建议

```
模块一（模板编辑，含写盘+校验）
        │  模板是参数规格的来源
        ▼
模块三（预设编辑，消费规格做校验/陈旧检测）   ← 可与模块一并行做"前端增强"部分
        │
        ▼
模块二（机床配置编辑，完整性校验依赖"模板引用的 machine 键"集合）
```

**建议顺序**：
1. **先做共用底座**：安全的写盘能力（原子写 + 路径穿越 + 乐观锁）+ 一个**统一的写 API**（CLI 与 UI 共用内核，P4）。这是三个模块的共同前置。
2. **模块一**：验证写盘底座（模板是最纯粹的文件资产）。
3. **模块三**：前端基线已存在，先补"持久化后端 + 陈旧检测 + 跨模板复用"，可较早交付用户价值。
4. **模块二**：最依赖前两者（完整性校验要枚举模板引用的键），放最后。

## 8. UI 落位与拆分方案（硬约束正面回答）

### 8.1 硬约束复述（实测）

- `ui/index.html` 与 `cli/ui/index.html` 两份必须同步（测试 `ui_html_copies_stay_in_sync` 拦）。
- 当前 **2735 行**，硬上限 **3000 行** → **余量仅 265 行**（比文档记的 2685 更紧）。
- `cli` 通过 `include_str!("../ui/index.html")` 内嵌单文件，故 **`ui/` 不可排除**，运行时仍是单文件。

### 8.2 落位决策

> **默认：CLI 为主，UI 为辅（分层落位）。**

| 模块 | CLI（主） | UI（辅） |
|---|---|---|
| 模板编辑 | `template new / edit / derive / rename`（写盘、校验、并发防护全在 CLI/core） | 只读展示 + 「在外部编辑器打开」+ 保存后刷新预览。**不在浏览器内做自由文本落盘** |
| 机床配置 | `machine add / edit / remove`（写 `nctool.toml`）+ `--from generic` | 若做，须是 **schema 驱动表单**（20 键 + Choice 下拉 + 完整性提示），非原始 JSON |
| 预设 | `preset save / list / load / rm / export / import`（文件后端） | 沿用现有 chips；新增"差异预览/陈旧标记/跨模板应用"小交互；数据经 API 与 CLI 同源 |

**为什么 CLI 为主**：
1. 编辑器是**低频、高风险**操作，不值得为它撑爆 UI 单文件。
2. 写操作 = 新攻击面，CLI 走本地文件权限模型，**不引入新的 HTTP 写端点**（最小化风险）。
3. CLI 可被 `cli_e2e.rs` 直接守护，契约可测；浏览器交互难测。

### 8.3 硬上限 3000 行怎么办（三选一，按推荐排序）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐，P0）** | **不加界面**：三个模块的编辑能力全部放 CLI，UI 增量 < 265 行（仅按钮 + fetch + 轻量弹窗） | 零拆分成本；不碰同步测试；风险最低 | 浏览器内体验偏弱 |
| **B（P2，若坚持浏览器内富编辑）** | **构建期拆分**：源码拆为 `ui/src/*.part.html`，脚本拼装生成 `ui/index.html` + `cli/ui/index.html`；同步测试改为"生成物 == 提交物" | 保留单文件运行时与 `include_str!`；余量问题彻底解决 | 引入构建步骤，改开发流程 |
| **C（P2 备选）** | **第二页面**：新增 `ui/editor.html` 由 server 提供，同样内嵌 | 页面隔离，主 UI 不受影响 | 需处理两页路由、共享样式/脚本；`include_str!` 需加一份 |

**明确不做**：把编辑界面硬塞进现有单文件（会立刻突破 3000 行上限并违反同步约束）。

### 8.4 拆分触发条件（给架构师的护栏）

- 若任一 UI 改动使 `ui/index.html` 预计 > 2900 行 → **必须先执行方案 B**。
- 拆分后仍须满足：`ui/index.html` 与 `cli/ui/index.html` 字节一致；`include_str!` 路径不变。

## 9. 风险与安全要求

### 9.1 写操作引入的风险

| # | 风险 | 说明 | 必须的缓解 |
|---|---|---|---|
| R-1 | **路径穿越** | 模板名/机床 id 作为文件名 → `../` 逃逸模板根 | 复用 `validate_template_name`；写前 `canonicalize` 校验在根目录内；拒符号链接逃逸（沿用 D14 双层校验） |
| R-2 | **并发覆盖** | 两人/两进程同时改同一文件，后写覆盖先写 | 乐观锁（mtime/内容指纹）；冲突时中止 + diff + 另存分支 |
| R-3 | **半成品写入** | 写中断留下损坏文件 | 原子写（临时文件 + rename） |
| R-4 | **存储型 XSS** | 模板名/预设名/机床 id 回显到 UI | 沿用已修复的 `esc()`（含引号）覆盖所有**新**插值点（09-19 审查已确认基线，新字段不得破） |
| R-5 | **无鉴权的本地写端点** | 若新增 HTTP 写 API，回环内任意本地进程可写 | 写端点**仅回环**（沿用）；不新增自由文本落盘端点；如需 token 则一次性 token（P1-4 未做项） |
| R-6 | **破坏 golden 基线** | 改模板/清单会动 21+3 golden | 写操作**不自动**改 golden；提示人工 `NCTOOL_UPDATE_GOLDEN` + diff 复核（B4.2） |
| R-7 | **静默出错** | 预设/机床非法值静默落盘 → 后续静默产出错误 G-code | 写前校验阻断；未知键仅告警（保留扩展语义）但 Choice/完整性必须阻断 |
| R-8 | **削弱安全提示** | "更省事地生成 G-code"可能让人忽略"未经工艺评审" | 试渲染/预设应用界面**保留**"模板与预设未经真实工艺评审、上机前须复核"提示（不得折叠或默认隐藏） |
| R-9 | **契约漂移** | 新增命令改变退出码/JSON 包络 | 严守 0–7 退出码矩阵与 `--format json` 包络；`cli_e2e.rs` 44 用例须全绿 |
| R-10 | **服务层既有债** | P1-19 无读超时/无并发上限（未修） | 新增写端点不得放大该风险；优先只读+文件后端方案 |

### 9.2 研发必须遵守的安全底线（红线）

1. **写路径必须经统一入口**，不得各命令各写一套文件 IO（P4 单一来源）。
2. **写前必校验、写中必原子、写后必报告**；校验失败**不得**落盘。
3. **模板/机床 id 一律当作不可信输入**做路径与字符校验。
4. **不得**为省事放宽 `Choice` 合法性、缺键阻断、`line_number_digits` 夹紧等既有防线。
5. **不得**新增绕过校验的写入口（P3）。
6. **不得**在 UI 引入新的未转义插值点。
7. **golden 与退出码契约**：改动若影响，必须走人工复核 + 全量回归。
8. **安全提示文案**（未经工艺评审）**不得**因新功能被移除或弱化。
9. 新增持久化文件（如 `presets.*`）**不得**被写进模板根目录从而被当作模板发现（避免污染注册表）。
