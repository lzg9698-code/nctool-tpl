1技术选型与架构决策

1.1 桌面框架对比：Tauri 2 vs Electron vs egui

nctool-tpl 的核心逻辑全部用 Rust 编写，以 nctool-core 纯库形式存在。桌面框架的选择直接决定了 Rust 代码的复用方式和最终包体积。

推荐：Tauri 2 — 可核对的两条依据：① nctool-core 是纯库（core/src/lib.rs 不依赖任何 GUI / HTTP / 进程框架），WebView 侧零 FFI 即可复用；② 已有的本地服务层 cli/src/server.rs::route 是无网络依赖的纯函数，其端点集合由 scripts/api_routes.json 单一来源 + CI parity 门禁约束，Tauri command 可以复用同一批处理函数而不是另起一套。
需要澄清的现状：仓库文档（ARCHITECTURE.md / ROADMAP.md / PROJECT_STATUS.md）中没有任何桌面端或 Tauri 规划（全仓搜 tauri 零命中），因此本方案是新增交付面、而非既有规划的落地。现有前端资产是 ui/index.html（151,342 字节，源码为 ui/src/*.part.html 7 个片段，经 scripts/build_ui.mjs 逐字节拼接生成，并同步产出 cli/ui/index.html 供 include_str! 打包）——它不是"138 KB 单文件"，迁移成本应按片段化源码评估。

1.3 与 nctool-core/cli 的集成方案

Tauri 后端（src-tauri/）既可以直接依赖 nctool-core / nctool-tpl，也可以在 cli 增加 lib target 后进程内复用它的服务层。两条路径的差别只是"复用多少既有契约"：

  • 复用既有契约（推荐） — cli/src/server.rs::route 是纯函数，已经把"参数下溢守卫（api_body → json_underflow_error）→ 模板解析 → 校验 → 渲染"整条链路封装好，端点集合由 scripts/api_routes.json 单一来源约束。Tauri command 调用这些函数后，GUI 与 Web UI 行为天然同源，CI 的 param / option / api-routes 三道 parity 门禁也能顺势覆盖 GUI。
  • 直连 core（仅在确需新能力时） — nctool-core 提供 TemplateRegistry / validate_template / pipeline::GCodeGenerator / manifest::Manifest / asset::* 写盘内核；nctool-tpl 提供 Renderer 与 lint。Renderer 与 lint 都不在 nctool-core 内，core 只是它们的调用方 —— 这是 v1.0 最容易踩错的一处。
  • 类型安全 — ParamSpec / ParamValue / ParameterSet / ValidationReport / LintFinding / MachineConfig 均已实现 serde；ParameterSet 的 Deserialize 是手写的，同时接受扁平键与 values 两种形式，可直接映射为前端 TS 类型。
  • 不要弃用本地服务层 — 下溢守卫与 parity 门禁都在这一层。GUI 可以不在进程里监听 HTTP（直接调 route() 即可），但不能绕过这套处理函数自己解析参数；nctool ui 本身也继续保留（并存策略见 1.5 节）。
  • 写盘一律走 core::asset — 模板 / 机床 / 参数预设的增删改使用 TemplateWriter / MachineWriter / PresetStore（原子写 + fnv1a64 乐观锁指纹 + 清单同步），不要在 GUI 侧直接 fs::write 模板或配置 —— 那会绕开清单一致性与并发冲突检测。

1.5 交付面边界：与 CLI / Web UI 的关系（v1.1 新增）

引入 GUI 后仓库会有四个交付面：nctool CLI、nctool ui 本地 Web UI、Tauri 桌面 GUI，以及 CI 覆盖的 parity 契约集。边界必须先定，否则同一功能出现两套实现、"修一处漏一处"——而这正是本项目反复强调要避免的静默错误类型。

方案做法收益代价
A. 进程内复用 cli 服务层 推荐 给 cli 增加 src/lib.rs（保留 bin），Tauri command 调用 server::route 或其底层命令函数 下溢守卫、端点集合、错误分类全部继承；GUI 与 Web UI 行为同源，parity 门禁可扩展覆盖；不会出现两套参数解析 cli 由 bin-only 改为 bin+lib；Ctx 内的 RefCell<Option<(RegistryKey, Rc<GCodeGenerator>)>> 不是 Send/Sync，需改为 Mutex/Arc 或按命令重建（重建 = 重新解析全部模板，需实测耗时）
B. 直连 core / tpl 自建命令面 在 GUI 内重新实现参数解析、校验编排、错误映射 不必调整 cli 结构；命令面可自由发挥 必须自行复刻下溢守卫与 api_routes.json 契约，否则三端行为漂移；新增端点要改的位置从 3 处变成 4 处
C. GUI 只做外壳（内嵌 tiny_http 或复用 nctool ui） 前端换壳，后端仍走本地 HTTP 改动最小，最快拿到"可安装的桌面窗口" 要处理端口占用与来源校验；原生能力（文件对话框、托盘、自动更新）仍需自己补
建议：Phase 1 走方案 A，把"契约复用"当作第一个交付物而不是后期优化；若需要尽快演示桌面外壳，可用方案 C 过渡，但不要走 B —— B 的每条自建路径都会成为 parity 门禁之外的盲区。
并存策略：nctool ui 与桌面 GUI 长期并存，面向不同场景（无安装权限/远程访问的机器 vs 工业 PC 本地部署）。只有在 GUI 覆盖了 Web UI 的全部端点、且 parity 门禁已把 GUI 纳入硬门禁之后，才考虑降低 Web UI 的维护优先级。
门禁扩展：任何新增端点必须同时改动四处并在 CI 落地 —— 后端路由臂、scripts/api_routes.json、Web UI 的 API 封装、GUI 的 command 封装。

2c. 静态检查页（Lint + Validate）

本页承载两类语义不同的检查，v1.0 把它们混在一起按 ERROR/WARN/INFO 分级展示，会让界面承诺一个后端给不出的结论，故在此拆开：

lint（nctool_tpl::lint）validate（core::validate::validate_template）
检查对象模板源码文本模板源码 + ParamSpec + 本次参数集
现有规则仅 1 条：三角函数度制风险（sin/cos/tan 以弧度为单位，NC 程序几乎总是度制）13 类 IssueKind：Missing / TypeMismatch / NonFinite / OutOfRange / NotInteger / NotInOptions / ConditionalSkipped / DeriveFailed / Unused / SpecInert / ShadowedSystemVar / ParseError 等

交互场景设计方案

实时预览刷新 变量表单变更 → onChange → 300ms 防抖 → invoke('render_template') → 更新右侧 NC 代码。参数以原始 JSON 文本传递（见 3.4 节），渲染失败时预览区显示红色错误信息且不中断编辑。预览区右上角显示绿色脉冲点表示「实时更新中」。

参数范围提示 ParamSpec 的 min/max/options 字段驱动输入约束。数值超范围时输入框边框变橙，tooltip 显示推荐范围。枚举类型（options）自动渲染为下拉框。
模板搜索 模板管理页顶部搜索框，输入即筛选（按名称、描述、分类匹配），支持模糊匹配。
多窗口对比 Phase 2 功能：可从渲染页「在新窗口打开」创建独立渲染实例，方便对比不同参数的输出结果。

3.4 参数输入通道与安全约束（v1.1 新增，必读）

Tauri 的 IPC 在调用命令前就把入参 JSON 反序列化成 Rust 类型，命令体拿到的是已解析的值。本仓库有一条硬约束正好卡在这个位置上：JSON 数字下溢 —— 1e-400 这类"真值非零但过小"的十进制字面量会被 serde_json 静默解析成 0.0，这个 0.0 会一路写进 G-code，全程不报错（ERR-NUM-UNDERFLOW，属于"错误程序上机床"级别的静默错误）。

既有 Web UI 之所以安全，是因为参数走 HTTP：cli/src/server.rs 在处理请求时先在文本层扫描（api_body → json_underflow_error → core::json_num::scan_underflow_candidates + serde_json 实测确认），确认下溢直接硬失败。因此 GUI 的接口设计必须满足两个条件：

约束做法反例（v1.0 的写法）
命令必须拿到原始文本 render_template(params_json: String, ...) —— 参数以 JSON 字符串形式传入（前端 JSON.stringify 后再放进 invoke 参数），Rust 侧先扫描文本、确认后再交给 serde_json/ParameterSet params: HashMap<String, ParamValue> —— 到达命令体时 1e-400 已经变成 0.0，文本层信息永久丢失，无法补救
复用既有处理函数而不是重写 按 1.5 节 方案 A 调 server::route("/api/render", ...) 或同等函数，守卫逻辑零复制 在 GUI 内自行 serde 解析参数（等于把守卫删掉）
参数模型用真实类型 ParameterSet（core 已实现 Deserialize，同时接受扁平键与 values: {...} 两种形式） 自定义 HashMap<String, ParamValue> 结构（与 CLI/Web UI 的参数契约不同源）
落地与验收：① render / validate 两个命令签名改为接收 params_json: String；② 首个 spike 就要跑一条对抗用例 —— 传 {"x": 1e-400}，期望报错且不产出 G-code（与 CLI --format json 的行为一致）；③ 该用例应同时进入 CI，覆盖 CLI、Web UI、GUI 三条入口，避免将来某一端被"优化"掉守卫。
注意：--lenient（宽松模式）不豁免这类错误 —— 下溢属于"用户传入的参数值不合法"，是硬失败，不受宽松模式影响。

4Tauri Commands API 设计

以下 Tauri commands 是对既有契约的薄封装，通过 #[tauri::command] 暴露给前端 React 调用（invoke('command_name', args)）。三条硬规则贯穿本章：

  • 参数入口一律是 params_json: String —— 参数以 JSON 原文传入，先过下溢守卫（3.4 节），再交给 ParameterSet。不要用 HashMap<String, ParamValue> 直接接参。

  • 错误沿用既有分类 —— 复用 CLI 的 CliError（args / render / io … 对应退出码）与 TplError / WriteError 的语义，映射为前端可判别的 {kind, message}，不要新造一套文案。

4.6 AppState、线程模型与错误映射（v1.1 新增）

议题约束做法
State 必须 Send + Sync #[tauri::command] async fn 的 State<T> 要求 T: Send + Sync；而 cli::Ctx 内部是 RefCell<Option<(RegistryKey, Rc<GCodeGenerator>)>>（单线程缓存，注释明确写"无需加锁"） 方案 A 落地时把该缓存改为 Mutex<Option<(RegistryKey, Arc<GCodeGenerator>)>>，或每条命令重建 GCodeGenerator（代价 = 重新解析全部模板，需实测；先用基准数据决定）
注册表缓存失效 缓存键含目录指纹，模板目录变动后必须失效，否则界面显示陈旧模板列表 沿用既有 RegistryKey 指纹比较；写操作（新建/编辑/派生/重命名/改机床）成功后主动失效缓存并刷新前端列表
长任务与取消 批量渲染/大模板可能超过 IPC 交互时限 用 Tauri 的异步命令 + 事件（progress event）汇报进度，不要阻塞主线程；Phase 3 的批量渲染按此设计
错误映射 前端需要能区分"参数非法 / 模板语法错 / 校验未通过 / IO 失败 / 并发冲突" 统一返回 { kind, message, detail? }：kind 取 CLI 既有分类（args / render / validate / io / conflict），conflict 用于乐观锁指纹不一致（UI 提示"文件已被外部修改"）
文件对话框与路径 Web 前端拿不到真实路径 用 Tauri dialog 插件在后端取路径，前端只传"用户选了哪个"的意图；路径校验走 asset::path::SafePath / validate_asset_name，防越出模板根
