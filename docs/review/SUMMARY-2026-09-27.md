## 2. P0-致命（3 条）

### P0-1　乐观锁是 check-then-write，全 crate 零互斥 → 并发写静默互相覆盖

- **位置**：`core/src/asset/mod.rs:72-88`（`WriteKernel::write_guarded`）；佐证：`asset/template.rs:100-109`
- **问题**：宣称"绝不静默覆盖他人改动"的乐观锁，实际是「读快照 → 比对 → 写」三步，无任何跨进程/跨线程互斥。全 `core/src` 内 `flock` / `lock_exclusive` / `create_new` / 锁文件检索结果为 **0 处**；`guard.rs` 名为锁、实为 FNV-1a 指纹计算。
- **影响**：CLI 与 HTTP 服务（`server.rs` 的 `/api/presets` 与 CLI 写同一个 `presets.yaml`）并发运行时，两个写者同时通过比对，后 `rename` 者胜，先写者的一整次编辑**静默丢弃**，且双方都收到 `Ok(Updated)`。丢失的是机床参数/预设参数值，直接进 G-code 渲染 —— 属本项目零容忍的"渲染成功但结果错误"。
- **建议（经架构师二次裁定，见 §3.1）**：新增 `core/src/asset/lock.rs`，`DirLock::acquire(target)` 建 `<target>.nctool.lock` 并加 **OS 级 advisory lock**（Unix `flock(LOCK_EX)` / Windows `LockFileEx`；Rust 1.89+ 可直接 `File::lock()`），`Drop` 解锁，`write_guarded` 改为「取锁→读快照→比对→写→释放」。
- **⚠️ 已撤回的建议**：初稿曾建议 `create` 分支走 `OpenOptions::create_new`（`O_EXCL`），**已撤回** —— ① 持锁后 `expect = None` 的检查即为真原子，冗余；② `O_EXCL` 必须直接写目标文件，用不上 tmp+rename，崩在半路会留下**残缺的新文件**，正是 `atomic.rs:6-8` 要避免的形态 —— 堵了并发却引入崩溃残留，是反向交易。撤回后 `template_duplicate`(6) / `name_conflict`(6) 的对外退出码契约**一行都不用改**。
- **锁的分层口径（写死）**：锁解决「写-写交叠」（跨进程）；`expect_hash` 乐观锁解决「读-改-写」的 ABA（含跨会话）。**两层都要保留，锁不替代乐观锁**。
- **实现细节**：选 OS 级 advisory lock 而非"锁文件存在即锁定"的轮询 —— 进程被杀时 OS 自动释放，**不会留下陈旧锁**，无需 TTL/stale 检测；锁文件只 unlock 不 unlink（Unix 上删文件会让 flock 失效）。

### P0-2　主轴转速上界 6000 硬编码，与机床 `max_spindle_rpm` 完全不联动（F1 风险，已确认成立）

- **位置**：`core/src/registry.rs:951`（硬编码点）、`registry.rs:931`（发射 S 值的模板行）、`core/src/machine.rs:76`（WFL=3500）、`machine.rs:96`（INDEX=5000）、`machine.rs:310-313`（schema 默认 6000）、`machine.rs:405`
- **证据**：
```rust
// core/src/registry.rs:944-952
crate::validate::spec("spindle_speed", ParamKind::Integer, true, None, "主轴转速（S 值，正整数）")
    .with_range(1.0, 6000.0)      // ← 静态常量，与 machine 无关
    .with_unit("r/min"),
```
**交叉核实**：`max_spindle_rpm` 在 `core/src/registry.rs` 出现 **0 次**，在 `templates/**` 出现 **0 次** —— 机床侧声明了上限，模板与校验两侧无人消费。
- **影响**：`wfl_m65`（上限 3500）下 `--param spindle_speed=5000` 校验**全绿**，输出 `M3 S5000` —— 超速 43%，且无任何运行时提示。**CNC 物理后果**：主轴/刀柄超速 → 刀具断裂、工件飞出、主轴轴承失效，属可致人伤的机床事故。同时违背 `core/src/validate.rs:905-907` 自己写下的承诺（"主轴转速上界……由 `ParamSpec` 的 `min`/`max` 表达"）。
- **建议**：`ParamSpec` 增 `max_from: Option<String>`；`validate.rs` 增 `resolve_bound()`，沿 `check_vars`(:385) → `check_var_values`(:640) → `check_value_constraints`(:908) 透传 `machine: Option<&MachineConfig>`；机床侧值非法时回退静态值**并报警告**（绝不静默用 0 当上界）；`registry.rs:951` 改为 `.with_max_from("machine.max_spindle_rpm")`；错误消息点名机床。
- **前置依赖**：`machine.rs:347-353` 的 `validate_config_keys` 对 Integer 键只验"能否解析"（`"0"`/`"-100"`/`"999999999"` 全通过），必须先补范围校验，否则联动后一个 `0` 会全量误杀（见 Q-12）。

### P0-3　HTTP 500/400 响应原样回显内部错误正文，泄漏模板绝对路径

- **位置**：`cli/src/server.rs:535`（validate）、`637`（render 校验）、`672`（render 渲染）、`354`（template_detail）、`1196`（inspect）
- **问题**：这五处绕过本模块自己建立的 `internal_error`（`server.rs:1364-1370`），直接把 `RegistryError`/`PipelineError` 的 `to_string()` 塞进响应体，而这些错误正文**含模板文件绝对路径**。
- **影响**：用户名/目录结构/磁盘布局外泄给任何能连 `127.0.0.1:<port>` 的本地进程（零权限零认证），DNS rebinding 下还可被网页读走。已有测试 `server.rs:3188-3203` 专门钉"500 正文不得含路径"，但**只测了 `internal_error` 本身，没覆盖这五条泄漏路径** —— 门禁是绿的，漏洞在"有门禁"的错觉下长期存在。
- **建议**：`535/637` 改 `internal_error(CliError::from(e))`；`672` 改 `cli_error`（400）；`354/1196` 保留 400 但确保 `CliError::from(RegistryError)` 不带路径。**补回归测试**：构造含绝对路径的错误，分别对 `/api/validate`、`/api/render` 发请求，断言响应体不含 `Users` / `:\\` / `.j2`。

## 4. P2-一般（38 条，按域归类）

**写通道与 IO（6）**
- `preset.rs` 一次 `upsert` 共 4 次全量文件 IO + 1 次全文下溢扫描（`313-314`/`340+347`/`365+372`/`mod.rs:89`），同时拉长 P0-1 的 TOCTOU 窗口
- 清单二次完整 YAML 解析（`manifest.rs:440-441` + `461-462`），加下溢扫描共 3 趟
- `normalize()` 的 `base.join(name)` 分支会拼出重复文件名（`preset.rs:671`，当前不可达，但"修好"父目录 canonicalize 后立刻产出错误路径）
- 吞错：`template.rs:253` 读取失败被折叠成"文件必须不存在"；`guard.rs:82` 静默降级到 `UNIX_EPOCH`
- `WriteError::Conflict` 的 Display 不含 `expected`/`actual`，`--expect-hash` 排障看不到
- 临时文件无启动清扫：进程在 `write_tmp` 与 `rename` 之间被杀 → `.nctool-tmp-*` 永久残留

**并发与 API 设计（5）**
- `TemplateWriter::rename` 完全无乐观锁（`template.rs:153-163`），与 `save` 不对称
- `TemplateEntry.source_text` 是 pub 可变字段而 `analysis` 是私有缓存（`registry.rs:136-159`），不变式靠"调用方记得调 `invalidate_analysis()`" —— 漏调一次则基于旧源码校验新源码，结论全错且不报错
- `TemplateRegistry` 用 `std::cell::OnceCell` → `!Sync`（`registry.rs:159`/`330`），HTTP 侧只能整体 `Mutex`、所有请求串行
- `manifest ⟷ registry` 双向依赖（`manifest.rs:27` ↔ `registry.rs:154`），两个枚举应下沉到 `model.rs`
- 公共 API 表面积过大 + 双路径导出（`lib.rs:31-72` 约 40 个 re-export 与 `asset/mod.rs:28-42` 重复）

**校验与数值（8）**
- `spec_map` 用 `HashMap::collect()`，同名规格静默"后者胜"（`validate.rs:393-394`/`702-703`）
- 有限性检查递归深度上限 32 超限后静默 return（`validate.rs:762-765`），与"宽松模式唯一硬失败项 = NonFinite"有缝隙
- `line_col` 每个候选做一次 O(n) 前缀扫描（`json_num.rs:648-655`），O(m·n)
- `nc_strip` 无数量级上限（`src/filters.rs:113-124`），与模块文档"NC 过滤器附带数量级上限防护"不符；`1e300` 会输出 300+ 位数字串
- `validate_config_keys` 对 Integer 键只验"能否解析"（`machine.rs:347-353`）
- 派生链的源参数拿不到变量库的类型/区间约束（`variables.rs:198-215`、`derive.rs:229-231`）
- part 层无法覆盖 `line_number_start/step`（`part.rs:104-119`），超长零件静默断号
- 资产名未拒绝 Windows 保留设备名（`CON`/`NUL`/`COM1`/`LPT1`）、尾随点空格、超长路径（`asset/path.rs:15-40`）

**CLI / HTTP（10）**
- `server.rs:1358` 的 `panic!` 位于请求处理循环内；`1324/1341` 每个响应都重新构造 Header + `expect`
- `to_string_pretty(..).unwrap_or_default()`（`output.rs:377/386`、`lint.rs:59/94`、`validate.rs:52`）序列化失败产出**不含 `ok` 字段的畸形包络**
- `context.rs:387-407` `tree_stamp` 任一失败即返回 None → `build_registry` 静默放弃缓存，退化为全量重建（5.7~16ms）且无提示
- 默认值三处副本：行号步进 `10`、上限 `9999`；`1 MiB` 两个独立字面量
- 两套模板解析（`render.rs:161-224` vs `templates.rs:112-137`）；`machine test --template` 只接受注册表名，render/validate 接受文件路径 —— `--template` 语义不统一
- 下溢守卫漏 2 个端点（`server.rs:1135`/`1171`）；`presets_delete` 缺 `validate_asset_name`
- CLI 与 HTTP 的预设保存**校验顺序相反**（CLI：值校验→归属；HTTP：归属→值校验），同一份输入两通道结论不同
- `/api/templates` 用 `registry.list` 暴露隐藏模板，CLI 用 `list_visible` 需 `--all`，且 HTTP 响应项不带 `visible` 字段
- 无 `OPTIONS` 预检处理；`completion.rs:12` 未走 `write_stdout_quiet`（BrokenPipe panic）
- `$EDITOR` 按 `split_whitespace()` 切分，含空格路径的编辑器打不开；非 UTF-8 路径用 `to_string_lossy` 当注册键

**一致性（1）**

## 5.1 跨模块定稿契约（架构师 × 工程师已对齐，两份报告口径一致）

本次审查中 core 侧的修复会打到 CLI 层，两处契约经双方对齐后定稿，**避免了两份报告给出矛盾指引**：

### 契约 1　新增 `WriteError::LockBusy { path }` → CLI kind `write_conflict`（退出码 6），**不新增 kind**

- **依据**：核对 `output.rs:119-133` 与 `output.rs:500-511` 的退出码矩阵，确认 6 的语义是"渲染/注册表/**写冲突**失败"，锁争用正属此类。复用已有 kind → 退出码矩阵、README 表、`exit_code_matrix` 测试**零改动**。
- **明确反对归 `io`(3)**：`output.rs:104` 的消息是"读写失败"，会把用户引向查权限/磁盘，方向错；且 3 在脚本里通常被视为硬失败，会误杀本可重试的场景。
- **消息文案另给** —— 锁争用 ≠ 内容被改，不能复用 `output.rs:78-82` 那条。
- **⚠️ 落地风险（决定实施顺序）**：`WriteError` 是 `#[non_exhaustive]`，`output.rs:105` 与 `:271` 都有 `_ => io(3)` 兜底 → **不显式登记也能编译过，但会静默退化成退出码 3**。因此**必须先落地 P1-11（6 份映射收敛为一张 `classify_write_error()` 表）**，之后加 `LockBusy` 只需往表里加一行；否则要手工改 6 处，漏一处即静默错分。

### 契约 2　`registry.rs:733` 采用**降级方案**，不改 `new()` 签名

- **原因**：`new()` 一旦返回 `Result`，`impl Default for TemplateRegistry`（`registry.rs:738-742`）就保不住（`Default` 必须返回 `Self`），而 `Default` 被 `GCodeGenerator::default()`（`pipeline.rs:373-377`）依赖 —— 冲击面比 CLI 调用点更大。
- **定稿**：内置模板注册失败 → 跳过该模板 + 记入 `TemplateRegistry::builtin_warnings()`，注册表照常可用。**CLI 零改动**，仅新增一个可选展示能力（`nctool doctor`）。
- **加守卫测试**：每个内置模板单独 `nctool_tpl::parse` 断言成功，把"minijinja/nctool-tpl 升级踩雷"从"用户运行时 panic"提前到"CI 变红"。

### 其余对齐结论

- **`asset/template.rs:326` 的 NBSP panic 不改签名**：`indent_of` 只认 ASCII 空白 + `l.get(key_indent..)`，`manifest_entry_body` 仍返回 `Option<Vec<String>>`，`None` 语义仍是"条目不存在"而非"解析失败" → **CLI 侧已有的降级分支不用动**。
- **去重说明**：`registry.rs:399`（`add_file` 无界读）由架构师认领并计入 P1-1，**与 CLI 侧的无界读同源，汇总时只计一次**。

### 交接问题的裁定（工程师交接、架构师已收工，由主理人查证定稿）

**问题 1　`TemplateRegistry::builtin_warnings()` 的方法名与签名** —— 定稿如下：

```rust
/// 内置模板安装失败的记录（降级方案的可见性出口）。
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct BuiltinWarning {
    /// 未安装的内置模板名
    pub name: String,
    /// 失败原因（`RegistryError::Compile` 的 Display，已含模板名与行列）
    pub message: String,
}

impl TemplateRegistry {
    /// 内置模板安装失败列表；正常情况下为空。
    /// 非空即意味着有内置模板缺失，必须在 stderr / `/health` 暴露，不得静默。
    pub fn builtin_warnings(&self) -> &[BuiltinWarning] { &self.builtin_warnings }
}
```
- 返回 **`&[BuiltinWarning]`**（切片而非 `Vec`，避免每次 clone；与同文件 `renderer()` 返回 `&Renderer` 的风格一致）。
- `message` 直接取 `RegistryError::Compile` 的 Display —— 它已含模板名与行列，不必另造文案。
- **已查证 `add_entry` 是「先校验后入库」**（`registry.rs:347-361`：empty → duplicate → `renderer.add_template()` 编译 → **然后**才 `entries.insert()`）。因此「失败即跳过」不会留下半入库状态，降级方案安全。

**问题 2　若用户模板 `include` 了内置模板，而该内置因降级缺失 → 显式解析错误还是静默空内容？**

**结论：会显式报错，不会静默变空。且当前代码库根本不存在这种引用。** 三条证据：

1. **全库 `{% include %}` 只有 2 处，都是文件→文件**（`templates/turning/undercut_es.j2:21`、`undercut_fs.j2:27` → `turning/_undercut_common.j2`）。内置 `program_header` / `tool_change` 只被注册表单独登记使用，**无任何模板 include 它们**。
2. **无 `ignore missing` 用法**（全库 grep 为空）—— 没有把缺失降级为空的开关。
3. **`templates/README.md:261-267` 自己写明**：include 必须写全路径，短名即 `❌ TemplateNotFound`。

因此即使将来有人 include 内置模板，缺失时 minijinja 抛 `TemplateNotFound`（硬错误），经 `src/error.rs` 的 `nested_error_chain` 会带上模板名与行号 → **显式可见**。

**但由此暴露一个真实缺口（新增建议，P2）**：该错误**只在渲染阶段才出现**，`nctool lint` 不报 —— `lint` 只看单文件 AST，不解析 include 目标。建议在 `validate`/`lint` 增加「include 目标是否可解析」的跨文件检查；至少做到：`builtin_warnings()` 非空时，`lint` 输出提示而非静默通过。

### 实施期新增的三条硬约束（工程师在建表时发现）

**约束 A　`LockBusy` 的 HTTP 文案不得照抄 `Conflict` 分支 —— 否则新开一处路径泄漏**
`LockBusy` 要求 `Display` 消息带 `{path}`，但 `server.rs:1411-1417` 的 `Conflict` 分支把 `path.display()` **直接写进了 HTTP 响应体**（这正是 P1-9 预设绝对路径外泄的一部分）。实施者若照抄一个 `LockBusy` 分支，就会**新开一处同类泄漏** —— 而 P0-3 正是要堵这类洞。
→ `classify_write_error` 表增设 `cli_msg_with_path` 字段做**双通道分离**：CLI/stderr 带 path，**HTTP 一律脱敏**。表里 8 个变体的 kind / HTTP 状态 / 双通道消息已全部写死，接手者不会漏。
（事实纠正：`write_error_resp` 并**不**调 `err.to_string()`，是逐变体手工 `format!` 的；调 `Display` 的只有 `output.rs:103`。）

**约束 B　HTTP 通道必须用非阻塞 try-lock（等待时间 = 0）**
`serve_requests` 是单线程顺序循环且 tiny_http 无读超时（P1-8）。HTTP 请求若在 `route()` 里阻塞等锁 2s → **整个 UI 停顿 2s**，与 P1-8 叠加更糟。→ 服务侧锁等待时间设为 0，拿不到即返回 409。

**约束 C　`registry.rs:733` 的降级方向对本项目更危险，警告必须够响**
降级方案（跳过 + `builtin_warnings()`）虽避免了 panic，但**崩溃立刻可见，而"某个内置模板悄悄不存在"不会** —— `templates list` 只少一项、`render drill_cycle` 只报 404。这是"静默产出错误程序"红线，**比 crash 更难察觉**。
→ 三个配套必须一起落地：① 每进程 stderr 打一次；② `/health` 加 `"builtinWarnings"`（纯新增，不破契约）；③ 守卫测试 + 现有 `route_templates_list`/`part_generate_*` 作天然哨兵。

## 9. 结论

这是一个**文档质量与工程自觉都相当高**的项目 —— 几乎每一处非显然的设计都写了"为什么"，且大量注释明确标注了"不要这样改"的理由与实测数据。但本次审查暴露出一个系统性模式：

> **"声称的保障与实际的机制不匹配"** —— `guard.rs` 名为锁实为指纹、`write_guarded` 名为锁实为 check-then-write、`create` 注释自认非原子、`source_text` 的缓存不变式靠调用方自觉、`nc_strip` 承诺数量级上限却裸奔、转速上界承诺由 `ParamSpec` 表达却写成与机床无关的常量。**每一处都写了详尽的文档解释为什么，却都把"真正落地机制"留给了未来。文档质量掩盖了机制缺失 —— 这比没有文档更危险，因为它会让 review 者误以为已经解决了。**

因此建议的收尾原则不是"补更多文档"，而是：**逐条把已写下的承诺兑现为可执行的机制与测试，并为每条承诺配一条会红的守卫测试。**

### 10.2 报告结论的四处**实测更正**（照原文改会改错）

1. **P1-12 的可达性不成立**。报告称"目标模板被删/语法坏时 `preset apply` 会输出『陈旧检测: 通过』"。
   实测：`specs_of(ctx, &target)?` 会**硬失败**（模板被删 → 退出码 5；语法坏 → 退出码 1），根本走不到陈旧检测。
   真正的问题只是代码里 `unwrap_or_default()` 这个**写法**（吞 `Err` 假装空集），已按"不得静默"改掉；
   测试改为钉住**真实**保护点（`apply_fails_loudly_when_target_template_is_unresolvable`）。
2. **P1-5 的"Windows 上同样有效且开销可忽略"过于乐观**。实测：`File::open(目录)` 直接 `PermissionDenied`（os error 5）；
   加 `FILE_FLAG_BACKUP_SEMANTICS` 能打开句柄，但**只读句柄** `sync_all()` 仍报 os error 5 ——
   必须**备份语义标志 + 写权限**。故加了非空转守卫 `parent_dir_can_actually_be_opened_for_fsync`（这条不省，否则实现写错会静默退化成空操作）。
3. **P1-7 只做"读失败报错"不够**。tiny_http 的 `EqualReader` 在底层 EOF 时返回 `Ok(0)`
   （`equal_reader.rs:52-58` 注释写明 "if the limit is reached, it returns EOF"）——**短读不报错**。
   只加 `Err` 分支，半包请求仍会被当完整请求送进 `route()`。必须**自己比实际字节数与 `Content-Length`**。
4. **P1-8 建议的 `std::thread::scope` + `recv_timeout` 不起作用**。`scope` 在块结束时会 **join 全部线程**，
   读线程仍卡在 `read` 上 → 主线程照样钉死。必须用 `std::thread::spawn` **分离**出去；
   代价是被放弃的连接会留下一个挂着的线程，故必须配 `MAX_IN_FLIGHT_BODY_READERS` 上限闸（否则把"挂死"换成"线程无限增长"）。

### 10.3 本轮**新发现**：P0-1 的修复自身在 Windows 上有缺陷

`DirLock::try_open` 原先一步 `OpenOptions::create(true).write(true).open()`。Windows 上
**两个线程并发首次创建同一个尚不存在的文件**时，落败者的 `CreateFile(OPEN_ALWAYS, GENERIC_WRITE)`
既不返回 `ERROR_SHARING_VIOLATION(32)` 也不返回 `ERROR_FILE_EXISTS(80)`，而是 **`ERROR_ACCESS_DENIED(5)`**。

- 实测（本机，`200` 轮）：文件不存在时 **200/200** 出现恰好一个 `os error 5`；同一文件**已存在**时 **400/400** 全部成功。
- 后果：`map_io` 把 `PermissionDenied` 归类为 `WriteError::ReadOnly` → 并发写的落败者被报成"文件只读"，
  **盖掉了它本该得到的 `Conflict`**，于是 `concurrent_writes_to_same_path_never_corrupt` 在 Windows 上**恒红**（不是 flaky，是每次必红）。
- 修法：先 `create_new`（`CREATE_NEW`），落败者拿 `AlreadyExists` 后回退普通 open（该路径实测 400/400 无失败）。
  **不**采用"短睡重试"——那是给时序假设买单；`create_new` 直接消掉了"并发创建"这个动作本身。
- 守卫：`concurrent_first_lock_file_creation_is_not_misreported_as_readonly`（钉住归因：并发首次取锁只允许 `held` / `LockBusy`）。

> 教训与 §9 的结论同源：**文档写了机制，但机制本身在真实平台上没被测过**。P0-1 的测试写在 Windows 上却从未在此平台上跑过。

### 10.4 本机环境阻塞（**与代码无关**，但会挡住本地门禁）

本机（Windows 11 + Rust 1.89/1.98）**无法 spawn 带 piped stdin 的子进程**：任何程序、任何工具链、
关掉沙箱都一样，`std::process::Command` 配 `stdin(Stdio::piped())` 一律
`os error 231 ERROR_PIPE_BUSY`（`stdin(Stdio::null())` / 继承则正常；Python 的 `subprocess` 正常）。
最小复现：`examples/` 临时探针 5 行即可（已删）。

后果：
- `cli/tests/*` 全部 7 个 `assert_cmd` 构造点走 `assert_cmd 2.x` 的 `spawn()`，而它在 `cmd.rs:511` **无条件**
  `self.cmd.stdin(process::Stdio::piped())`，且**没有** `get_mut` / `Deref` 出口 → 无法在不替换 assert_cmd 的前提下绕过；
- `cargo test --doc` 同样失败（rustdoc 以管道 spawn `rustc`）。

**不受影响**：`--lib` / `--bins` / core 的 `--tests`（合计 864 + 547 项全绿）、`fmt` / `clippy -D warnings` /
四个 JS 门禁 / 真实二进制的手工 E2E。**受影响**：`cli/tests/*`、`--doc`、覆盖率门禁（少了集成测试的覆盖）。
建议先修环境（疑似安全软件的过滤驱动拦截 `\Device\NamedPipe\` 的读打开），CI（Ubuntu）不受此影响。

#### 10.4.1 覆盖率门禁的读数必须按此校正（**不要误判成代码退化**）
