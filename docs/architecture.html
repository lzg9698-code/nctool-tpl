01分层架构与依赖方向

依赖严格单向向下：cli → core → tpl → minijinja。不存在反向依赖，也不存在跨层依赖。 所有真实业务逻辑都在 nctool-core，CLI 与未来的 Web UI 只是两个输入/展示面，不复制业务逻辑。

03核心模块

八个模块撑起全部能力：模板层负责"读懂模板"，领域层负责"判断对错"，管线层负责"产出正确的代码"。

nctool-tpl　模板解析层

AST 遍历，提取全部引用 / 未声明变量 / 模板引用闭包，并判定可选与必选

minijinja Environment 封装，默认严格模式，宽松为显式 opt-in

error

6 个错误变体，从引擎详情反解变量名 / 过滤器名，带行列定位

05模板解析层数据流

一份模板源码裂变成两条路：一条经 AST 扇出为三个提取器，产物汇入校验层； 另一路交给 Renderer 配合过滤器集渲染，产物进入管线后处理。

图 3　模板解析层数据流

可选 / 必选判定规则（最容易写错的地方）

模板写法判定原因
{{ x }}必选裸引用，缺失即渲染失败
{{ x | default(0.15) }}可选兜底上下文，缺失仍可渲染
{% if x is defined %}可选同上
{{ x | nc_fixed(3) }}必选过滤器需要具体值求值，无法以空串替代
{{ (a+b) | default(1) }}必选兜底不向下传播：子表达式先求值，undefined 参与运算即报错
{{ a.b | default(1) }}必选同上，取属性先于 default 求值

若此处误判为可选，上层校验放行后严格模式渲染依然会失败 —— 只是把一个渲染期崩溃推迟成崩溃。

06参数校验数据流

输入三元组 —— 模板引用的变量 × 参数规格 × 用户参数集 —— 输出一份结构化的校验报告。 同一个报告在严格模式下决定"是否阻断"，在宽松模式下决定"降级哪些、保留哪些"。

输入

  • 未声明变量　来自 extract_undeclared，携带可选 / 必选标记
  • 模板引用闭包　include / extends 递归并入，防环
  • 参数规格　registry 提供：类型 / 区间 / 整数约束 / 默认值
  • 参数集　CLI、JSON 文件或 API 传入
  • 系统注入变量　默认 machine，视为已提供

检查项（按执行顺序）

  • 规格默认值自洽性　default 自己违反约束时报错（模板作者的错误）
  • 有限性　NaN / Inf 拒绝生成
  • 类型匹配　ParamKind::matches
  • 取值区间　min / max，含边界
  • 整数约束　规格标记 integer 但值带小数
  • 冗余参数　提供了模板未引用的参数（警告级）

IssueKind 九类结构化类别

Error Missing · TypeMismatch · NonFinite · OutOfRange · NotInteger · ShadowedSystemVar · ParseError

Warning Unused（冗余参数）

Other 未分类兜底

结构化类别的存在意义：调用方按类别而非消息文本做程序化决策。宽松模式要拦截 NaN/Inf， 正确写法是 report.has_kind(IssueKind::NonFinite)，而不是 message.contains("NaN") —— 后者脆弱且易失效。

07关键设计决策

每一条都是踩过坑之后的选择。写清"为什么"，比写清"是什么"更重要。

D1

minijinja::Value 单点再导出

nctool-tpl 是 workspace 里唯一声明 minijinja 依赖的 crate，并再导出其 Value； nctool-core 不直接依赖。原因：渲染上下文是公共签名的一部分，一旦两边解析到不同版本， 两个 Value 就是不同的类型，拼不到一起。单点持有把"版本漂移导致类型不匹配"从可能变成不可能。

D2

严格模式为默认，宽松为显式 opt-in

Renderer::new() 默认 UndefinedBehavior::Strict，模板引用缺失变量直接失败。 宁可让不完整的模板报错，也不能静默输出一段残缺的 G-code。

D3

校验前置于渲染

整个架构的主线。参数缺失、类型不符、越界、NaN/Inf 全部在渲染前拦截 —— 因为 G-code 是发给机床的指令，写错一个坐标就是撞刀。

D4

必选性由"模板实际引用"决定，而非规格声明

ParamSpec::required 只是文档性声明。实际必选性由模板引用 + 是否有 default 兜底决定， 因此 required 与 default 无互斥约束，可同时声明（"文档上必选，但缺失时可用默认值兜底"）。

D5

兜底不向下传播

default 只兜底直接裸变量操作数。{{ (a+b) | default(1) }} 里的 a/b 仍记必选 —— minijinja 先求值子表达式，undefined 参与运算即报错，default 来不及兜底。

D6

Integer 作为独立参数类型

程序号、刀具号、刀长补偿号天然为整数。若用 Number 承载：tool_num=5.5 输出非法字址 T5.5；prog=1.7 被 nc_pad 静默截断成 O0001 且不报错。 两者都不报错，但都会让机床做错事。整值浮点数视为合法整数（5.0 通过，5.5 拒绝）。

D7

IssueKind 结构化类别，禁止按消息文本决策

见第 6 节。宽松模式拦截 NaN/Inf 靠 has_kind(NonFinite)，不靠文本匹配。

D8

宽松模式仍硬失败 NaN/Inf

宽松模式不是"跳过校验"：它跑完整校验，再把除 NonFinite 外的 Error 降级为 Warning。 早期实现直接跳过 validate，导致 X{{ x }} 能吐出 XNaN。 参数缺失可以留空，但非法坐标会让机床走到错误位置 —— 宽松模式放行的是"参数可缺省"，不是"参数值非法"。

D9

include / extends 穿透校验 + 防环

被引用且已注册的模板，其必选参数同样参与检查，避免组合模板的参数缺失只能在渲染阶段才暴露。 同名变量必选性取"或"，环引用由 visited 集合防护。

D10

后处理的所有尺寸参数都夹紧上界

line_number_digits 是用户可编辑的字符串。若无上界，配置一个 1000000000 会让每一行都去分配 GB 级缓冲 —— 而 Rust 分配失败是进程 abort，不可捕获。上界取 32（而非对齐 nc_pad 的 1024）， 因为行号前缀作用于每一行，总分配量是 行数 × 位宽。同理 step=0 归一化为 1，递增用 checked_add 防溢出。

D11

输出格式语义分离：Gcode vs Text

Text 仅渲染，不 trim、不编号、不清空行、不做 ASCII 清洗，保留原始字节； Gcode 才应用全部后处理。同一套引擎既能产出可上机的程序，也能用于任意文本生成。

D12

CLI 不复制业务逻辑

render 与 generate 是同一实现的两个入口，上下文构建、规格默认值兜底、 宽松渲染全部收编到 core 管线。集成测试的 golden 输出验证两者逐字节一致，这就是回归防线。

D13

配置损坏降级为警告而非错误

损坏的 TOML 降级为空配置 + warning 提示，不阻断命令。这样只读命令仍能用内置模板 / 机床， 用户也不会误以为配置已生效。只有确定是用户可修复的语法错误才降级；文件权限等 IO 错误仍然返回错误。

D14

CLI 参数类型推断的两个反直觉规则

--param x=007 推断为字符串（数值化会静默丢前导零，T007 → T7）； --param x=NaN 推断为字符串（非有限数不判为数值，避免文本被误判成数值传入上下文）。 需要精确控制时用类型后缀 k:s=v / k:n=v / k:b=v。

约束与已知边界

  • minijinja 版本锁定 ~2.24.0 —— 依赖 unstable_machinery（不稳定 AST API）与 debug feature，minor 升级可能破坏编译
  • 过滤器只保护自己产生的 NaN/Inf —— 裸 {{ x }} 与内建运算产生的非法值由 core 校验层拦截
  • 宽松模式下经过滤器引用的未定义变量仍会报错 —— 过滤器需要具体值求值
  • 机床预设值仅供开发测试 —— 投产前必须按机床手册核对 G/M 代码、轴配置与参数上限
  • 模板内容视为可信输入 —— 路径加载器防逃逸，但不防恶意模板逻辑
  • v0.x API 仍可能调整 —— 建议在 Cargo.toml 中锁定 minor 版本
