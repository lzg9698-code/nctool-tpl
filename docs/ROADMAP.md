### 1.3 关键判断

**这个项目当前不缺功能，缺"可信"。**

CLI 已经能完成「模板 → 参数 → G-code」全流程，功能面是完整的。但一个发往机床的指令生成器，
在**没有经过工艺工程师逐行核对、没有在真实机床上空运行验证**之前，它的"能用"是虚假的。
因此本路线图把 **阶段 A（领域验证）放在所有新功能之前**，并且在 MVP 裁剪时把它列为不可砍项。

## 4. 阶段详解

---

### 阶段 A — 需求与设计收口

| 项 | 内容 |
| --- | --- |
| **目标** | 让"正确性"可被证明。冻结 1.0 的 API 契约与功能范围 |
| **周期** | 3–5 人日（+ 外部评审等待时间） |
| **优先级** | **P0 — 不可推迟** |
| **依赖** | 无（起点） |

#### 关键任务

**A1. 工艺正确性评审（本阶段的核心，不可跳过）**
- 逐行核对 5 个内置模板的 G/M 代码：模态组冲突、字址合法性、循环取消、坐标系初始化
- 重点复核已知敏感点：`drill_cycle` 无 G1 前缀（G1 与 G81 同属 01 组模态）、
  `tool_change` 的 M3 主轴启动、`program_header` 的 `program_prefix` 拼接
- 核对 3 个机床预设的键值是否符合对应机床手册
- 产出《工艺核对清单》，每条模板/配置标注：已核对 / 待确认 / 不适用

**A2. golden 基线扩充**
- 现状：4 个 golden 文件（drill_cycle / program_header / program_footer / tool_change）
- 目标：5 内置模板 × 3 机床预设 = 15 组基线，覆盖 `safe_move` 与全部机床组合
- 每组固化：渲染输出 + 校验报告

**A3. 冻结 1.0 API 契约**
- 明确 `nctool-tpl` / `nctool-core` 的公共 API 在 1.0 前不再变动
- 补齐 `#[non_exhaustive]` 与 `missing_docs`
- 列出 1.0 前的破坏性变更清单及迁移说明

**A4. 定义 MachineConfig 键名 schema**
- 现状：模板依赖 `machine.xxx` 键名，但键名集合无 schema，拼错不报错（只在缺失时取默认）
- 产出：键名清单 + 类型 + 默认值 + 是否必填，并在 `registry` 层做校验（未知键告警）

**A5. 需求确认（对应 §2 的 Q1–Q11）**
- 逐条对齐或确认默认假设
- 明确 1.0 的**功能边界**（做什么、明确不做什么）

#### 交付物

| 交付物 | 说明 |
| --- | --- |
| 《工艺核对清单》 | 逐条标注核对状态，未通过项有处置结论 |
| golden 基线 15 组 | `tests/golden/` 下，纳入 CI |
| API 冻结清单 | 1.0 前的公共 API 与破坏性变更说明 |
| MachineConfig schema | 键名/类型/默认值/必填定义 |
| 需求确认纪要 | Q1–Q11 的结论 |

#### 验收标准

- [ ] 5 个内置模板全部通过工艺评审，无"待确认"遗留项（或遗留项有明确的降级处置）
- [ ] 3 个机床预设值已按手册核对，或文档显著声明"仅供开发测试"
- [ ] `cargo test` 覆盖 15 组 golden 基线，全绿
- [ ] API 冻结清单已写入 CHANGELOG

#### 风险

- **A-R1**：找不到工艺工程师 → 见 §2 Q2 的降级预案（定位下调为开发工具 + 显著声明）
- **A-R2**：评审发现内置模板有实质性错误 → 优先修复再继续，不得带着已知错误进入下一阶段

| 项 | 内容 |
| --- | --- |

| **周期** | 3–4 人日 |

**B1. 代码收口（最高优先，1 天内完成）**

**B2. 发版固化**

### 阶段 C — UI 服务与前端联通

| 项 | 内容 |
| --- | --- |
| **目标** | `nctool ui` 启动本地服务，浏览器看到的是**真实后端**的模板库，而非演示数据 |
| **周期** | 5–8 人日 |
| **优先级** | P1 |
| **依赖** | B |
| **可推迟** | ✅ 是（见 §7） |

#### 关键任务

**C1. `ui` 子命令与静态资源**
- 实现 `commands/ui.rs`（当前为占位）
- `include_str!` 内嵌 `ui/index.html`
- 默认绑定 `127.0.0.1:8787`，支持 `--host` / `--port` / `--open`
- **仅绑定回环地址**，拒绝非回环绑定（除非显式 `--host` 且打印安全警告）

**C2. 只读 API**
- `GET /api/templates?category=`
- `GET /api/templates/{name}`（源码 + 参数规格 + 提取变量）
- `POST /api/inspect`
- 统一返回 `{ ok, data?, error? }`

**C3. 前端切换到服务模式**
- **关键**：把 `API.mode` 从 `demo` 切到 `server`
- **核对演示模式与真实渲染的语义差异**（D5）——自研迷你 Jinja 与 minijinja 行为可能不一致，
  需逐项比对：过滤器行为、未定义变量处理、数值格式化
- 演示模式保留为离线兜底，但在 UI 上显著标注"演示模式结果可能与真实生成不一致"

**C4. 前端列表/详情联通**
- 模板列表（分类筛选 + 搜索）
- 模板详情（源码 + 自动提取的参数表，含必选/可选/默认值/行列定位）

#### 交付物

| 交付物 | 说明 |
| --- | --- |
| `nctool ui` 可用命令 | 启动、打开浏览器、正常退出 |
| 3 个只读 API | 含集成测试 |
| 前端服务模式 | 列表/详情走真实后端 |
| 《演示模式差异清单》 | 迷你渲染器 vs minijinja 的行为差异与处置 |

#### 验收标准

- [ ] `nctool ui` 启动后浏览器可打开，列出全部内置 + 目录模板
- [ ] API 集成测试通过（不依赖前端）
- [ ] 确认仅监听回环地址；`--host 0.0.0.0` 时打印安全警告
- [ ] 前端详情参数表与 `nctool inspect` 输出一致

#### 风险

- **C-R1**：**演示模式与真实渲染语义漂移**（D5）——本阶段最容易翻车处。应对：先做差异清单再切换
- **C-R2**：内嵌静态资源导致 binary 体积膨胀 → 可接受（单文件 ~100KB 级），但需记录基线体积

### 阶段 D — 完整交互闭环

| 项 | 内容 |
| --- | --- |
| **目标** | 浏览器内完成「选模板 → 填参数 → 实时预览 → 校验 → 下载」全链路 |
| **周期** | 8–12 人日（本路线图中最大的一块） |
| **优先级** | P2 |
| **依赖** | C |
| **可推迟** | ✅ 是（见 §7） |

#### 关键任务

**D1. 写 API**
- `POST /api/validate`（渲染前校验，返回结构化 `ValidationReport`）
- `POST /api/render`（参数 + 机床 + 生成选项 → 输出 + 报告）
- 严格/宽松模式开关

**D2. 参数表单自动生成**
- 由 `extract_undeclared` + 规格生成：必选高亮、可选带默认值、按类型渲染控件
- 数值参数带 `min`/`max`/单位提示

## 7. MVP 裁剪策略

### 7.1 核心判断

**CLI 本身已经是 MVP。** 它能完成「模板 → 参数 → G-code」全流程，能进 CI，能脚本化批量。
所以真正的裁剪问题不是"砍 UI 还是砍 CLI"，而是**"先保正确性还是先做体验"**。

答案明确：**先保正确性。**

### 7.2 三档裁剪方案

| 档位 | 触发条件 | 保留范围 | 产出 | 工期 |
| --- | --- | --- | --- | --- |
| **档 1（时间砍半）** | 工期压到 3–4 周 | A + B + F 的发版部分 | **可信的 CLI 1.0**（无 Web UI） | 12–18 人日 |
| **档 2（标准）** | 工期 6–8 周 | A + B + C + E + F | **CLI 1.0 + 只读 Web 浏览**（UI 只能看，不能生成） | 20–28 人日 |
| **档 3（完整）** | 无强工期约束 | A–F 全部 | **CLI 1.0 + 完整 Web 工作台** | 26–40 人日 |

> **档 2 的性价比最高**：C 阶段只做只读 API（5–8 人日），就能让浏览器成为模板库浏览器，
> 而 D 阶段（8–12 人日）换来的是"表单填参"的体验提升 —— 对懂 G-code 的工艺工程师而言，
> `--param k=v` 并不比表单难用。**D 是最应该被推迟的阶段。**

### 7.3 绝不能砍的三项

| # | 不可砍项 | 理由 |
| --- | --- | --- |
| 1 | **工艺正确性评审**（A1） | 砍掉等于交付一个可能撞刀的工具。这是整个项目存在的意义 |
| 2 | **三机床 golden 基线**（A2） | 唯一的回归防线。没有它，任何改动都可能静默破坏已验证的输出 |
| 3 | **发版与安装验证**（F1） | 没发版 = 没人能用 = 所有工作不产生价值 |

### 7.4 人力受限时的取舍顺序

按此顺序从下往上砍（先砍最下面的）：

```
  A 需求与设计收口      ← 保留（除非放弃项目）
  B 基础架构稳固        ← 保留（债务不清零，后面全是坑）
  C UI 服务联通         ← 第三优先保留
  D 完整交互闭环        ← 第二优先砍
  E 联调测试            ← 部分保留（安全加固随 C 做）
  F 上线与迭代          ← 发版部分必留，文档/Backlog 可延后
  ─────────────────
  Backlog: part 批量 / 模板编辑 / 参数预设 / 模板库扩充 / i18n  ← 最先砍
```

### 7.5 单点阻塞时的降级预案

| 阻塞点 | 降级预案 |
| --- | --- |
| 找不到工艺工程师（Q2 失败） | 项目定位下调为「**模板开发工具**」而非生产工具；README 与所有文档显著声明"未经工艺验证，投产前必须自行核对 G-code" |
| 无法引入 HTTP 库（依赖管控） | UI 改为纯静态：CLI 导出 JSON，前端读取本地文件（保留演示模式的离线能力） |
| 前端复杂度失控 | 砍到档 2（只读浏览），或只保留 CLI |
| 只剩 1 周 | 只做 M0（代码安全提交）+ M1 的最小集（golden 扩到 safe_move），其余全推迟 |
